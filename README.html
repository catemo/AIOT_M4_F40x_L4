2这是什么

proL4_p1.3_blink_v2.1b 是一个"会闪灯"的四层工程。本工程（IOT_M4_L4）在它上面加了三件事：串口、DHT11、WiFi-MQTT 上云。

【1.3 串口章节】
串口助手敲：LED1 ON  ↵        →  板上 LED1 亮，回 "OK: LED1 ON"
串口助手敲：LED1 OFF ↵        →  板上 LED1 灭，回 "OK: LED1 OFF"
串口助手敲：BLINK    ↵        →  恢复 1 Hz 闪烁，回 "OK: BLINK"
串口助手敲：STATUS   ↵        →  回 "LED1=ON"（读真实引脚电平）
串口助手敲：HELP     ↵        →  回命令表

【1.4 DHT11 章节】板子自己每 2 秒吐一行：
[DHT11] Temp=28.0C | Hum=55.0%        →  温度 ≥31 ℃ 点亮 LED1，湿度 ≥60 % 点亮 LED2
[DHT11] Read FAILED (stage=1)         →  读不到就报"卡在哪一步"，且两颗灯都不动

【2.2 上云章节】同一块板子自己连 AP、连 Broker、每 5 秒上报一组：
[MQTT] MQTT connected (keepalive=30s)
[MQTT] subscribed: $oc/devices/<id>/sys/commands/#
[MQTT] Published: {"services":[{"service_id":"Sensor","properties":{"temperature":28.0,"humidity":55.0}}]}
云端下发命令 → [MQTT-CMD] LED_Control led=1 → 板上 LED1 亮 → 回 result_code=0

四层里的空目录，是分三步被填满的：

层v2.1b（纯闪烁）+串口章节+DHT11 章节+上云章节（2.2）
① appapp_led / app_blink / app_task新增 app_cmd（命令解析）新增 app_dht11（周期采集）+ app_link（阈值联动）新增 app_mqtt（连接分段 / 周期上报 / 命令响应）
② platform空目录mod_uart1（统一入口）不设（DHT11 没有中间知识）新增 mod_mqtt（四种报文 + 剩余长度编码）+ mod_wifi（连 AP / 建 TCP 的语义动作）
③ network空目录net_uart（DMA + IDLE + 环形缓冲）无新增 net_esp8266（AT 会话 + +IPD 分流）；net_uart 扩成实例表，一条代码带 USART1 与 USART3
④ perceptionper_led / per_gpio扩出 PER_LED_On/Off/IsOn、per_gpio_write/is_on新增 per_delay（TIM2 微秒底座）+ per_dht11（单总线）零新增（UART 引脚与 DMA 在 CubeMX 里配；AT 是文本帧处理，属网络层）

3硬件与环境

项目配置
MCUSTM32F407ZETx（Cortex-M4F，168 MHz）
用户 LEDLED1 = PG14（温度指示）、LED2 = PG13（湿度指示），均为低电平点亮（写 0 亮 / 写 1 灭）
调试串口USART1：PA9 = TX，PA10 = RX，115200-8-N-1
接收方式DMA2_Stream2 循环模式 + USART IDLE 空闲中断判帧 + 环形缓冲
上云串口USART3：PB10 = TX，PB11 = RX，115200-8-N-1（接 ESP8266 的 RX/TX，交叉接）
上云接收DMA1_Stream1 / Channel 4 循环模式 + USART3 IDLE 判帧 + 两段缓冲（AT 文本 512 B + +IPD 载荷 256 B 环形）
WiFi 模组ESP8266（ESP-01S / ESP-12F 均可），AT 固件；只支持 2.4 GHz AP，5 GHz 连不上
云平台华为云 IoTDA，MQTT 明文 1883（AT 固件不做 TLS 握手，不用 8883）
温湿度传感器DHT11 单总线，DATA = PG9（上电必须 High）；模块 VCC 3.3 V；裸传感器须在 DATA-VCC 间外接 4.7k~10k 上拉
微秒时基TIM2，APB1 定时器时钟 84 MHz → Prescaler = 83 → 1 计数 = 1 µs，只 Base_Start 不进中断
系统时钟HSE 8 MHz → PLL（M=8 / N=336 / P=÷2）→ SYSCLK 168 MHz，AHB 168 / APB1 42 / APB2 84 MHz
HAL 时基TIM6（供 HAL_Delay 等使用）
看门狗IWDG 独立看门狗（片上外设，不占引脚）：LSI ≈32 kHz，分频 64 × 重载 1500 → 超时 3.0 s；任务每 500 ms 喂一次；串口敲 HANG 可演示"卡死 → 整机复位"
RTOS 节拍SysTick，configTICK_RATE_HZ = 1000 → 1 tick = 1 ms
RTOSFreeRTOS 10.x + CMSIS-RTOS2（osThreadNew / osDelay），动态创建，堆 32768 B（六个任务栈 512+1024+768+2048+2048+512）
中断优先级USART1 / USART3 / DMA1_Stream1 抢占优先级均为 5（与 configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY 相等，本工程统一纪律：ISR 内不调 RTOS API）
调试口SWD（ST-Link / J-Link 均可）

⚠ APB1 定时器时钟是 84 MHz，不是 42 MHz：APB1 预分频 ≠1 时定时器时钟 ×2。 所以 TIM2 的 PSC 必须是 83（84 MHz / 84 = 1 MHz）。填 41 会让所有 µs 计时减半，DHT11 必然读不到数。 三个定时器的分工：SysTick = FreeRTOS 独占、TIM6 = HAL 时基、TIM2 = 本工程微秒底座； DWT 的 CYCCNT 刻意不用（调试器下载后它常常不计数）。

上云是可选的：APP_MQTT_WIFI_SSID 等 8 个宏在 user/app/Inc/app_mqtt.h 顶部， 不填就只会看到 [MQTT] retry #1 in 2s 一路退避——本地三条链照常工作，不会因为连不上云而卡住板子。

两个动手就能验证的动作：

  • 手指捏住 DHT11（或对它哈气）→ 温度升到 ≥31 ℃ 时 LED1 亮；
  • 隔着 5 cm 对传感器哈气 → 湿度升到 ≥60 % 时 LED2 亮；
  • 拔掉 DATA 线 → 每 2 秒报 Read FAILED (stage=1)，且两颗灯保持不乱动；
  • 在华为云控制台下发 LED_Control {led:1} → 板上 LED1 亮，串口吐 [MQTT-CMD] LED_Control led=1 + [MQTT-CMD] response sent；
  • 串口敲 HANG 回车 → 打 [WDT] HANG cmd: stop feeding, reset in ~3s...，约 3 秒后整机复位、LED 快闪自检重来，

这次启动行变成 [WDT] boot: last reset = IWDG watchdog——"被狗咬醒"的证据。

灯不亮、串口没反应、或 DHT11 读不到，先按常见问题排查。

5串口命令怎么玩

命令作用回应
LED1 ON点亮 LED1（并让它退出闪烁）OK: LED1 ON
LED1 OFF熄灭 LED1（并让它退出闪烁）OK: LED1 OFF
BLINK恢复 1 Hz 闪烁（半周期取自 cfg）OK: BLINK
STATUS查询 LED1 真实电平LED1=ON / LED1=OFF
HANG卡死演示：看门狗任务罢工，约 3 s 后 IWDG 复位整机（2.4 新增）[WDT] HANG cmd: stop feeding, reset in ~3s...
HELP打印命令表见上
其它未知命令原样回显在方括号里ERR: unknown cmd [XXX]
  • 大小写不限（led1 on == LED1 ON），命令以回车结束；
  • 不发回车也能用：串口安静后会自动结算上一行（兼容"点一次发一次"的助手）；
  • 可打印字符会回显，这是判断"收链路通不通"最快的信号；
  • 输出全部是英文：源文件是 UTF-8，中文发到 GBK 编码的串口助手上会变乱码。

⚠️ 六个容易踩的坑

  1. *_TASK_STACK_SIZE 的单位是字节，不是"字"。填 256 以为省 RAM，实际只分到 256 字节 → 栈溢出会静默写坏 FreeRTOS 堆（不报错、不进 HardFault），现象是"跑几行后整机没反应"。
  2. "一键断 LED 链"在本工程已不成立：MOD_LED_ENABLE 改 0 会同时撞上 APP_UART1 requires APP_BLINK 与 APP_LINK requires PER_LED 两条闸门——串口命令、DHT11 联动、云端命令都要借 LED 链点灯。想让灯不自动闪，应关 APP_LED_ENABLE（保留状态机），让串口/云端接管。
  3. 关串口链要连带处理 DHT11 链、上云链、存储两条链与看门狗链：它们都要借串口打印，否则撞 APP_DHT11 requires MOD_UART1 / NET_UART3 requires HAL_UART_MODULE / APP_WATCHDOG requires MOD_UART1 / storage chain requires MOD_UART1。反过来关 DHT11 链不用手动补别的——日志应用层已由开关表达式自动跟关。
  4. 关到"没任务可建"会被拦：六个任务对应的开关都关、而 APP_TASK_ENABLE 仍为 1 → #error。
  5. 只关 APP_MQTT_ENABLE 省不下那 776 B RAM：UART3 的 DMA 缓冲（512 B）与环形缓冲（268 B）被 net_uart 的实例表项钉住，--gc-sections 不敢动。想真省 RAM 必须关总闸 MOD_WIFI_ENABLE。
  6. 物模型对不上 = 静默丢弃：service_id 或属性名与控制台"功能定义"不一致时，华为云丢弃且不报错——设备在线、串口打印 Published、云端"最新数据"永远空。

四条依赖红线：

① 只许 上层 → 下层 单向调用，不许回头、不许横向 include
② 例外：应用层可直达感知层（本地闭环，如按键点灯）
③ cfg/ 只被读、不被调用；common/ 被各层共用但自身不依赖任何层
④ HAL 只出现在感知层与网络层（网络层受 HAL_UART_MODULE_ENABLE 看管）

★ 命名约定：统一为 <前缀>_<模块>_<动作>，前缀标"在哪一层、是对内还是对外"：

  • 小写蛇形 = 驱动实现 / 业务流程：per_gpio_write、app_led_init、app_taskCreate、net_uart_read
  • 大写前缀 = 对外的"门卫 / 状态机 / 入口"接口：PER_LED_On、APP_BLINK_On、MOD_UART1_SendString

每层有自己独立的 LED 编号枚举（APP_BLINK_LED_t / PER_LED_t / PER_GPIO_LED_t），末位都是哨兵量 XXX_LED_COUNT——既作数组长度，也作越界判断。 注意三套的 COUNT 并不相同：感知层两套 = 2（管 LED1 与 LED2），APP_BLINK_LED_t = 1（LED2 不归闪烁状态机管，它只被湿度联动直接控制）。

为什么上云链要五跳？ 因为它有四种互不重叠的知识，任何一种都不能塞进别处： AT 指令怎么发、怎么等（net_esp8266）／"连网建链"是什么意思（mod_wifi）／ MQTT 报文长什么样（mod_mqtt）／报什么、多久报（app_mqtt）。 换模组只改 net_esp8266，换云平台只改 mod_mqtt 的主题与 JSON —— 这就是五跳的回报。

为什么感知层这次一个字都没加？ UART 的引脚与 DMA 在 CubeMX 里配（那是 Core/ 的事）， AT 是文本帧处理不是引脚时序 —— 它属于网络层。四层不是每层都必须加东西。

10设计要点

1. 串口三件套（网络层 net_uart.c）

① DMA 循环接收  一次配置，硬件自己转圈搬运，写满自动绕回，永不停止
② IDLE 判帧     总线一安静就进空闲中断，此刻把"新到的字节"切成一帧
③ 环形缓冲      中断只管塞，任务有空了再来取（SPSC，无需关中断）

判帧的核心数学（缓冲区 256、NDTR 递减计数）：

pos = 256 - __HAL_DMA_GET_COUNTER(&hdma_usart1_rx);   /* 硬件写到哪儿了 */
len = (pos >= start) ? (pos - start)                  /* 没绕回 */
                     : (256 - start + pos);           /* 绕回了，补一整圈 */
s_dma_last_pos = pos;                                 /* 记下搬到哪儿 */
/* 再从 DMA 缓冲拷进 ringbuf：跨末尾时分两段写 */

ISR 三条纪律：只搬数据、不解析不打印；不阻塞不等空位；不调任何 RTOS API。

2. 手动与闪烁互斥（应用层 app_blink.c）

错误：敲 LED1 ON → 直接点灯 → 500ms 后状态机又翻一次 → 灯莫名灭了
正确：敲 LED1 ON → APP_BLINK_On()
                     ├─ half_period_ms = 0    状态机从此跳过这颗灯
                     ├─ counter_ms     = 0    下次重启闪烁从零起算
                     └─ PER_LED_On()          再去点灯

顺序不能反：先停闪、后点灯。

3. 感知层为什么现在才用上 active_low

toggle 与亮灭方向无关（只翻 ODR），所以闪烁用不到它；write / is_on 是"亮灭语义"，必须查表翻译：

level = s_led_hw[i].active_low ? (on ? RESET : SET) : (on ? SET : RESET);

于是换一块"高电平点亮"的板子，改 s_led_hw[] 表里那一个数字就行——函数体、上层代码全不动。

4. 两条"永远存在"的接口

MX 生成文件里的调用点不受本工程开关控制，所以被它们调用的函数必须"永远存在"、关开关时变空壳：

8. DHT11 单总线的四道纪律（1.4 章节）

① 微秒底座必须是硬件定时器
     APB1 定时器时钟 84 MHz → PSC=83 → 1 µs/计数。
     不用 DWT 的 CYCCNT（调试器下载后常常不计数）、不用 HAL_Delay（只有 ms）。
     回绕靠无符号减法自动处理：(now - start) < us，32 位 71.6 分钟回绕一次。

② 关中断要"成对"，且所有失败路径汇到同一个出口
     40 位数据是 26~70 µs 的脉宽，任务切换或任意中断抢走几百 µs 就测错了。
     所以从"拉高起始信号"到"读完 40 位"之间 __disable_irq()（约 4~5 ms/次，占 2s 周期 0.3%）。
     ★ 所有失败路径一律 goto exit，在 exit 里统一 __enable_irq()
       —— 否则一次超时就让系统永远关着中断，这是本驱动最容易写错的地方。

③ 18 ms 起始信号刻意放在关中断【之前】
     它不是时序敏感段（差几毫秒传感器都认），放外面能少关 18 ms 中断。
     "能少关就少关"是硬规矩。

④ 输入方向配【浮空】而不是上拉
     配成上拉会与模块内已有的 4.7k 上拉形成分压，高电平拉不到位。

失败时报 stage=1~6，让"读不到数"这个笼统现象有 6 种具体答案：

stage含义去查
1完全没回应供电 / 接线 / PG9 / 上拉电阻
2 / 3响应只回了一半上拉 / 接触不良 / 线太长
4 / 5数据段异常电源纹波 / 线长 / 被长中断打断
6校验和错电气质量（干扰、供电不足）

9. 边沿触发：让闪烁与联动共存

LED1 同时被三处惦记：1 Hz 闪烁（Toggle 翻转语义）、串口命令（On/Off 绝对语义）、温度联动（On/Off 绝对语义）。 前两者靠"命令先清半周期退出闪烁"解决；温度联动若是每 2 秒都写一次 On/Off，闪烁就被挤掉了。

static uint8_t s_led1_state = 0xFFU;   /* 0xFF = 还没联动过，首帧必写 */
void APP_LINK_ApplyTemp(uint8_t temp_int)
{
    uint8_t want = (temp_int >= APP_LINK_TEMP_THRESHOLD) ? 1U : 0U;
    if (want == s_led1_state) return;  /* 状态没变：把灯让给闪烁 */
    s_led1_state = want;
    (void)(want ? PER_LED_On(PER_LED1) : PER_LED_Off(PER_LED1));
}

代价是"跨越阈值的那一瞬间可能与闪烁撞车一次"（概率极低、后果是灯闪一下）， 比"为了让位而关掉闪烁"划算得多。

10. 感知层只探测、不打印

PER_DHT11_SelfTest() 把自检结果填进 PER_DHT11_Diag_t 结构体，自己一句都不打印。 打印要走上层的 mod_uart1 → net_uart，感知层依赖上层会让依赖方向倒转、分层直接破产。 所以"测出来"与"表达出来"分在两层——应用层拿到数字，再决定把它变成哪一行文本。

同一条纪律在上云链上重演：net_esp8266 只把现场递上去（net_esp8266_get_last_resp()）， 由应用层的 app_mqtt_dump_resp() 决定把它变成 hex + ascii 一行文本。

11. 一条代码管两个串口：net_uart 的实例表（2.2 章节）

判帧那 20 行数学（NDTR → 位置 → 绕回 → 两段拷贝）与"是哪个串口"完全无关。 所以复制一份 net_uart.c 是错的——应该把"变的东西"进表、"不变的"留代码：

typedef struct {
    UART_HandleTypeDef *huart;      DMA_HandleTypeDef *hdma_rx;
    uint8_t *dma_buf;  uint32_t dma_size;
    ringbuf_t *ring;   volatile uint32_t last_pos;  uint8_t ready;
} net_uart_ctx_t;

static net_uart_ctx_t s_uart[NET_UART_COUNT] = { /* USART1 / USART3 各一项 */ };

函数首参从"无"变成 NET_UART_Id_t id（NET_UART_DBG=0 / NET_UART_WIFI=1）， net_uart_ctx(id) 做越界 + ready 双门卫，判帧代码一个字都没改。

★ 这张表是有代价的：只关 APP_MQTT_ENABLE 时 FLASH 能掉到与关总闸相同（35164 B）， 但 RAM 多 776 B —— UART3 的 512 B DMA 缓冲 + 268 B 环形缓冲被表项钉住， --gc-sections 不敢动。想真省 RAM 必须关 MOD_WIFI_ENABLE（详见架构文档第二节）。

12. 两条缓冲物理隔离 + +IPD 四步分流

AT 会话是文本行，MQTT 报文是二进制，混在一条串口上。所以分两个缓冲，谁也不踩谁：

缓冲大小装什么满了怎么办
s_resp_buf512 BOK / ERROR / WIFI GOT IP / SEND OK 这些文本行丢最旧的一半，保住最新状态
s_payload256 B 环形+IPD 里的二进制载荷（不追加 \n）丢最旧并置溢出标志（net_esp8266_take_overflow()）

+IPD 的坑不在"找"，在"没找全"——一帧可能被拆成两次 IDLE 中断才到齐：

① 找 "+IPD,"                  → 找到就往下走
② 读到冒号，取 data_len        → "IPD,45:" → 45 字节
③ 数据没到齐就退出，下次再拼   ★ 灵魂所在：这一步不写，报文必错位
④ 整段搬进载荷环

断线只认"独立成行"的 CLOSED（\r\nCLOSED\r\n 或行首 8 字节），不能按子串匹配—— MQTT 报文里也可能出现这 6 个字节。也不用 AT+CIPSTATUS：它的回显会插进载荷流里。

13. 六段连接 + 分段重连 + 退避（app_mqtt.c）

连接不是"一次调用"，是六段，每段都有自己的超时和失败语义：

段动作超时给短了 / 给长了会怎样
①AT 测活2 s——
②AT+CWMODE=12 s——
③AT+CWJAP="ssid","pwd"10 s短了：DHCP 还没回就判失败；长了：拖住重连
④AT+CIPSTART="TCP","host",18838 s短了：DNS 解析没完就放弃
⑤MQTT CONNECT2 s半开连接（TCP 在、MQTT 死）→ 强制 CIPCLOSE 重建
⑥SUBSCRIBE .../commands/#2 s订阅不上 = 永远收不到命令
  • 一律 osDelay，不用 HAL_Delay：HAL_Delay 是死等计数器、不让出 CPU，CWJAP 等 10 秒会让 1 Hz 闪烁定住、看着像死机。
  • 退避 2 / 4 / 8 / 16 / 30 秒，第 5 次起 AT+RST 复位模组。封顶 30 s 是因为路由器重启通常几十秒内恢复。
  • 三种"断"分开处理：WiFi 掉（CWJAP 失败）/ TCP 断（收到 CLOSED）/ MQTT 掉（CONNACK 超时）；

重连只补没成功的那几段，不是每次从头再来。

  • 离线缓存 16 条（≈80 秒窗口），队满丢最旧，恢复后每 500 ms 补一条。必须有界——不设上限会吃光 128 KB RAM。

14. 快照而不是队列（APP_DHT11_GetSnapshot）

上报任务不该"为了发一条数据去催传感器再读一次"——那会把 2 s 的采集周期打乱。 改成采集任务写、上报任务只读的三行接口：

APP_DHT11_Snapshot_t snap;
APP_DHT11_GetSnapshot(&snap);      /* 整体结构体拷贝，不持锁 */
if (snap.valid == 0U) { /* 还没采到过：如实说"没数据"，不编一个 0 上去 */ }

最差情况读到的是"上一组"，对 5 秒一次的上报完全够用，所以不需要互斥量。

13常见问题

串口一个字都收不到，怎么排查？

三板斧，从最可能到最不可能：

  1. 线接对了吗 —— 板子 PA9(TX) → 转串口 RX、PA10(RX) → 转串口 TX，必须共地；波特率 115200-8-N-1。
  2. IDLE 判帧的顺序对吗 —— USART1_IRQHandler() 里 __HAL_UART_CLEAR_IDLEFLAG() + net_uart_rx_idle_handler() 必须写在 HAL_UART_IRQHandler() 之前。顺序写反 = 永远检测不到总线安静，一个字节都收不到。
  3. DMA 真的拉起来了吗 —— HAL_UART_Receive_DMA() 返回 HAL_BUSY 时会一个寄存器都不写；net_uart_start_rx_dma() 里已做了"复位 RxState 再启动一次"的处理，别把它删掉。

还有一个最快的信号：敲字符有没有回显。

  • 有回显 → 收（RX）和发（TX）都通；
  • 没回显但板子在跑 → 问题在收；
  • 连开机横幅都没有 → 检查任务是否建起来（上电 LED1 有没快闪 3 次）。

灯不亮 / 不闪

  1. 烧录成功了吗 —— 看 verify 是否 OK，必要时全片擦除再烧；
  2. 引脚对吗 —— LED1 = PG14，低电平点亮；换板子要改 s_led_hw[] 与 .ioc；
  3. 节拍在跑吗 —— 在 APP_BLINK_process() 下断点，看是否每 1 ms 进来一次。

敲了 LED1 ON，灯亮了但过一会儿自己灭了

说明命令绕过了状态机：正确的入口是 APP_BLINK_On()（先清半周期），不是直接 PER_LED_On()。

串口每 2 秒冒出的 DHT11 读数，看着很乱

正常：DHT11 是周期吐字的，与命令行的回显/应答交织在同一条串口上。敲命令时看 OK: 即可。

DHT11 一直报 Read FAILED (stage=1)，怎么排查？

三板斧，从最可靠的证据开始：

  1. 看自检行的四个字段（上电时那一行为准）：
  2. TIM2= 不是 ≈1000 → TIM2 的 PSC 配错，所有 µs 计时都错，必然读不到；
  3. loop= 不是 1,0 → PG9 引脚不通（虚焊、引脚号写错）；
  4. bus=0 → 总线被外部拉低（缺上拉或短路）；
  5. resp=0 → 传感器完全没应答。
  6. 确认物理条件：模块 VCC = 3.3 V、DATA 与 VCC 之间有 4.7k~10k 上拉（裸传感器必须外接）、线长 < 20 cm、采集间隔 ≥1 秒。
  7. 看 stage 定位：1 = 完全没回应（查供电接线）；6 = 校验和错（查电气质量）。

温度到了，LED1 却没亮

先确认 APP_LINK_ENABLE 是 1（被裁掉了就只打印不点灯），再看阈值： APP_LINK_TEMP_THRESHOLD 默认 28 ℃——手指捏住传感器或对它哈气才能越过。

DHT11 读数在跳，但两颗灯都不动

要么联动被裁了（APP_LINK_ENABLE=0），要么阈值没到。 拔掉 DATA 线验证"失败安全"：应当只报 stage=1，两颗灯保持现状不乱动。

改了 cfg_param.h 但没生效

配置是编译期的：改完必须重新编译并重新烧录，不是在线可调的。

报 #error "..." 编译不过

这是设计好的。61 道闸门会在编译期拦下配置矛盾—— 比如关了闪烁状态机却还开着串口控灯，或关了串口链却还留着要打印的 DHT11， 或留着 NET_ESP8266_ENABLE 却把 NET_UART3_ENABLE 关了。 读 #error 后面的文字，它会告诉你是哪两个宏冲突。

上云一直 [MQTT] retry #1 in 2s，连不上

按报错那一行的 resp= 内容分三种情况（app_mqtt_dump_resp() 会把模组原始回显打出来）：

resp= 的样子说明去查
resp=0 (empty: check TX/RX & power)模组一个字都没回TX/RX 没交叉、模组没供电（3.3 V，峰值 300 mA）、EN 悬空
有内容但都是乱码波特率不对模组出厂常是 115200，但有些是 9600 —— 改 MX_USART3_UART_Init 的 BaudRate 或先用 AT 改模组
有内容且能读到 ERROR模组活着，只是这句指令不认看内容：CWJAP 报 FAIL = 密码错 / 5 GHz AP；CIPSTART 报 ERROR = 域名或端口错

[MQTT] WiFi connected 之后卡在 TCP connecting

  • 域名 vs IP：先用 ping 确认 xxx.iot-mqtts.cn 能解析；
  • 端口必须是 1883（明文 MQTT）。8883 是 TLS，AT 固件不做 TLS 握手，会一直等到 8 秒超时；
  • ESP8266 的 AT 固件对长域名 + DNS 较慢，CIPSTART 给了 8 秒，别改小。

串口打印 [MQTT] Published: ...，但云端"最新数据"是空的

最经典的一类"静默失败"：物模型对不上。华为云收到报文后按 service_id 和属性名匹配"功能定义"， 匹配不上就丢弃、且不回任何错误。所以设备在线、日志有 Published、云端却没数据。

逐个核对：APP_MQTT_SERVICE_ID（默认 "Sensor"）与属性名 temperature / humidity 必须与控制台逐字一致（大小写也算）。

云端下发了命令，串口没反应

  1. 订阅上了吗 —— 看有没有 [MQTT] subscribed: $oc/devices/<id>/sys/commands/#；

少一个 # 就只能收到"恰好叫那个名字"的主题，实际一条也收不到；

  1. 命令名对吗 —— 处理函数只认 led 这个字段（app_mqtt_parse_led()），别的字段会被忽略；
  2. 是不是立刻又灭了 —— 那说明绕过了状态机。正确路径是 APP_BLINK_On()（先退出闪烁），

直接写引脚会被 1 Hz 状态机在半周期后翻回来。

只在关掉 APP_MQTT_ENABLE 时 RAM 没降

不是 bug，是实例表的代价：UART3 的 512 B DMA 缓冲 + 268 B 环形缓冲被 net_uart 的实例表项钉住， --gc-sections 不敢回收。FLASH 能省（35164 B），RAM 仍多 776 B。想真省 RAM 必须关总闸 MOD_WIFI_ENABLE。

换了文件夹名，编译产物名字变了

CMakeLists.txt 用 get_filename_component(... NAME) 自动取文件夹名作为工程名。这是有意设计——方便一个模板复制成多个工程。

板子每隔约 3 秒自己重启，串口横幅一遍遍重打

九成是看门狗没人喂。先看 [WDT] boot: last reset = 那一行：

  • IWDG watchdog → 上次是被狗咬醒的：是不是敲过 HANG（预期内演示）？

否则查喂狗任务——APP_WDT_FEED_PERIOD_MS 改大到 ≥1500 ms 会被编译期闸门拦， 能编过却咬狗多半是任务没建起来（开关裁剪组合）或栈溢出；

  • power-on/others 却一直循环重打横幅 → 不是狗咬的，查供电与晶振；
  • 调试器单步超过 3 秒也会咬狗：per_iwdg.c 已调 __HAL_DBGMCU_FREEZE_IWDG()

（halt 期间 IWDG 停止计数），确认烧的是新固件。

void USART1_IRQHandler(void)
{
  /* USER CODE BEGIN USART1_IRQn 0 */
  if (__HAL_UART_GET_FLAG(&huart1, UART_FLAG_IDLE)) {
      __HAL_UART_CLEAR_IDLEFLAG(&huart1);
      net_uart_rx_idle_handler(NET_UART_DBG);   /* 网络层：按实例判帧 + 搬进环形缓冲 */
  }
  /* USER CODE END USART1_IRQn 0 */
  HAL_UART_IRQHandler(&huart1);
}

void USART3_IRQHandler(void)        /* 2.2 章节新增，逐字对称 */
{
  /* USER CODE BEGIN USART3_IRQn 0 */

      __HAL_UART_CLEAR_IDLEFLAG(&huart3);

  }

★ 中断里只调字节流层，而不直接调 net_esp8266_*： +IPD 分流要把"文本响应"和"二进制载荷"分到两条缓冲、还要跨中断拼半包， 这些是任务上下文的活。ISR 里只做"把新到的字节搬进环形缓冲"这一件事， 三条纪律（只搬数据 / 不阻塞 / 不调 RTOS API）一条都没破。

15与五层参考工程的关系

本工程是四层实现；src/refer/ 下有五层对照版本，两者讲同一件事、代码可互相对照：

五层（refer）四层（本工程）说明
L1_app（app_uart / app_led / app_task / app_dht11 / app_mqtt）user/app（app_cmd / app_led / app_blink / app_dht11 / app_link / app_mqtt / app_task）命令解析与业务不变；上云业务同样是"连接 + 上报 + 命令"三件事
L2_svc（svc_led 闪烁状态机 / svc_env 环境服务 / svc_conn 连接状态机）user/app（app_blink / 并入 app_dht11 / 并入 app_mqtt）服务层收进应用层：本工程只有一条上云链、一个联网模组，连接分段不值得单独成层
L3_plat（plat_uart / plat_led / plat_dht11 / plat_esp8266 31 行 / mqtt_port 168 行）user/platform（mod_uart1 / mod_wifi 116 行 / mod_mqtt 565 行）+ user/perception（per_led）+ （DHT11 不设）纯转发的 plat_esp8266 被扩成"状态归一 + 建链后切 MQTT 模式"；mqtt_port 原来是 paho 的移植层，四层版改成手搓报文（不再依赖 Middlewares/Third_Party/paho）
L4_bsp（bsp_uart / bsp_led / bsp_dht11 / bsp_delay / bsp_esp8266 604 行）user/network（net_uart 实例表 / net_esp8266 586 行）+ user/perception（per_gpio / per_dht11 / per_delay）串口驱动与 AT 会话都进网络层；GPIO / 单总线 / 微秒底座进感知层
L5_com（module_cfg + 4 子文件 + ring_buffer）user/cfg + user/common配置体系原样，环形缓冲移入横切 common/

两边口径怎么统一：四层（感知 / 网络 / 平台 / 应用）既是责任口径（出问题时定界"找谁"），也是本工程的代码口径（写码时定"文件放哪"）。

不变的纪律：命令只许上层 → 下层单向走；cfg 只被读不被调；错误"越靠上越能上报、越靠下越静默兜底"； 层要有自己的知识才配单独存在（所以串口三层、上云五跳、LED 两跳、DHT11 两层，四者都对）。

DHT11 章节移植自 src/refer/H743ZI_V6.x（H743 + 五层）。移植时改动的三件事： 引脚 PF11 → PG9；定时器时钟 240 MHz → 84 MHz（PSC 239 → 83）； 命名 BSP_* → PER_*，并按四层砍掉纯转发的 plat_dht11。 至于自检如何上报，也从"驱动内部直接打印"改成了"只填结构体、交给应用层表达"。

上云章节同样参考它（app_mqtt 1084 行 / bsp_esp8266 604 行 / mqtt_port 168 行）， 但三处刻意不同：① 不引 paho，四种报文手搓（省掉整个 MQTTPacket 目录）； ② 用明文 1883 而不是 TLS 8883（AT 固件不做 TLS 握手）；③ 中断里只调字节流层， +IPD 分流放在任务上下文。逐条理由见架构文档第七节。
